# Надёжная передача работ и очистка данных

## Цель

Устранить риски, при которых сервер принимает неограниченное тело запроса, преподаватель получает
неполную работу, удалённые аккаунты оставляют приватные файлы, а назначенная работа запускается в
«быстром режиме» вопреки настройке преподавателя.

Это первый релиз исправлений после аудита. Визуальные и доступностные изменения в него не входят.

## Потоковое ограничение тела HTTP-запроса

Новый чистый ASGI middleware находится снаружи FastAPI-обработчиков и оборачивает `receive`. Для
`POST`, `PUT`, `PATCH` и `DELETE` он считает фактически полученные байты каждого `http.request`.
Превышение лимита завершает обработку ответом `413` в стандартном API-формате с кодом
`request_too_large`; приложение не вызывает Pydantic, `request.body()` и запись временного файла.

Проверка `Content-Length` сохраняется как ранний быстрый отказ. Отсутствие или подделка этого заголовка
не влияет на итоговую защиту: лимит проверяется и для `Transfer-Encoding: chunked`.

Лимиты выбираются по маршруту:

- JSON и прочие обычные тела — `MAX_BODY` (1 MB);
- запись ученика — `MAX_AUDIO_BODY` (15 MB);
- изображение материала — 5 MB, то есть тот же предел, который уже применяет контроллер.

Middleware не меняет поведение запросов без тела и не добавляет требование `Content-Length`.

## Двухфазная отправка работы

### Состояния

У `submissions.status` появляются состояния `uploading`, `submitted` и `graded`.

- `POST /api/assignments/{id}/submissions` создаёт только `uploading`-попытку и возвращает её id,
  номер, срок и состояние.
- `POST /api/submissions/{id}/recordings` доступен только владельцу и только в `uploading`.
- `POST /api/submissions/{id}/complete` доступен только владельцу и переводит попытку в `submitted`.
- Проверка и оценивание не принимают `uploading`-попытку. Выборка, экспорт и карточки преподавателя
  по умолчанию исключают её полностью.

`submitted_at` фиксируется именно при `complete`, а не при создании черновика. Это делает порядок в
кабинете преподавателя и факт опоздания соответствующими фактической сдаче.

### Проверка состава записей

Сервер получает набор обязательных ответов из snapshot заданного варианта, а не доверяет клиенту:
пять ответов для задания 1 и по одному для заданий 2 и 3. `complete` требует ровно один файл для
каждого обязательного ответа, с допустимыми номерами задания и вопроса. Неполный набор отвечает
`409 submission_incomplete` и перечисляет отсутствующие позиции.

Повторная загрузка той же позиции заменяет предыдущую запись атомарно: новая физическая запись и
метаданные сохраняются до удаления старой, а потерянный старый файл попадает в очередь очистки.
После `complete` загрузки отклоняются с `409 submission_not_uploading`.

Клиент создаёт попытку, последовательно загружает записи с ограниченными повторами и вызывает
`complete` только после успешных ответов на все загрузки. При сетевой ошибке он не объявляет работу
сданной: показывает сохранённую попытку и действие «Повторить отправку». Для назначенной работы
локальный результат остаётся доступен, пока отправка не завершена.

## Долговечная очередь очистки приватного хранилища

Добавляется таблица `storage_cleanup_jobs` с идентификатором, JSON-массивом ключей, числом попыток,
временем создания и последней ошибкой. Она хранит только пути закрытого storage, без токенов и
пользовательских ответов.

Перед удалением аккаунта контроллер в одной транзакции собирает ключи его аудиозаписей, файлов
материалов и snapshot-изображений, создаёт cleanup job и удаляет учётную запись. После commit он
пытается удалить объекты сразу. При успехе задача удаляется; при любой ошибке сохраняется для повтора.

`runtime.init_database()` выполняет ограниченную best-effort обработку очереди и логирует результат;
сбой S3 или локального диска не мешает запуску сервиса. Операционная команда позволяет обработать
очередь вручную и возвращает ненулевой код, если после попытки остались ошибки. Повтор безопасен:
удаление отсутствующего объекта считается успешным.

Та же очередь используется для старого файла при замене записи. Поэтому пути не теряются ни при
частичной сетевой ошибке, ни при завершении процесса между SQL-операцией и удалением файла.

## Назначенные работы и быстрый режим

При запуске по назначению фронтенд принудительно устанавливает `fastMode: false`, скрывает или блокирует
переключатель и рассчитывает длительность только из задания. Сервер сохраняет `fastMode: false` для
попытки назначения, даже если старый или изменённый клиент передал иное значение. Обычный самостоятельный
тренинг сохраняет существующее поведение.

## Схема и совместимость

Новая Alembic-ревизия после текущего head добавляет `uploading` в допустимые состояния `submissions` и
создаёт `storage_cleanup_jobs` с индексом по времени создания. SQLite baseline не редактируется; чистая
и обновляемая базы достигают одной и той же итоговой схемы через Alembic.

Существующие `submitted` и `graded` работы остаются без изменений. Ранее созданные неполные работы не
переводятся автоматически, поскольку система не может доказать, что в них должны были быть все записи.

## Ошибки и наблюдаемость

Новые публичные коды: `submission_incomplete` (409), `submission_not_uploading` (409) и
`request_too_large` (413, существующий код). В audit log записываются создание и завершение попытки,
отклонённое завершение и успех/ошибка задач очистки. Содержимое аудио и ключи хранилища в лог не попадают.

## Проверка

1. Интеграционный тест отправляет payload больше лимита фрагментами без `Content-Length` и получает 413.
2. Интеграционный тест создаёт попытку, подтверждает её невидимость преподавателю, загружает полный набор
   и подтверждает видимость только после `complete`.
3. Интеграционные тесты проверяют неполный набор, повторную запись и запрет загрузки после завершения.
4. Unit-тесты очереди проверяют устойчивость к сбою хранилища и идемпотентный повтор.
5. Миграционные тесты проверяют чистую и обновляемую SQLite-базу.
6. JS-тест и Playwright-сценарий подтверждают, что назначение игнорирует быстрый режим.
7. Полный `make check`; для изменённого пользовательского сценария — `make test-e2e`.

## Границы релиза

В этот релиз не входят Range-поддержка для S3, редизайн кабинетов, доступность locked-контента и
мобильная вёрстка. Они будут следующей, UI-фазой после стабилизации этого процесса.
