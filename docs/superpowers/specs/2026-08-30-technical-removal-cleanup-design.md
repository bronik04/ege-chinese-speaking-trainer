# Техническая уборка: удаление исторического долга

**Статус:** согласовано в чате, ожидает проверки письменной спецификации

## Цель

Убрать из поддерживаемой поверхности проекта остатки уже закрытых подсистем, недостоверную документацию,
лишние production-зависимости и дублирующий frontend-код. После уборки публичные учебные сценарии,
API активных возможностей, существующие аккаунты, аудиозаписи и опубликованные материалы должны работать
как прежде.

Работа выполняется тремя независимо проверяемыми пакетами:

1. retired backend, зависимости и относящиеся к ним тесты;
2. активная документация и архив исторических документов;
3. CSS и нативные элементы выбора.

Каждый пакет заканчивается свежим `make check`. Для frontend-пакета дополнительно выполняется
`make test-e2e` и визуальная проверка основных экранов на desktop и ширине 390 px.

## Неприкосновенные данные и контракты

- Опубликованные Alembic-ревизии и замороженный SQLite baseline не редактируются и не удаляются.
- Legacy-таблицы групп, назначений, submissions и reviews остаются в существующих базах до отдельного
  решения о сроке хранения и миграции данных.
- Уже сохранённые review-assets продолжают читаться из прежнего физического каталога или S3-ключей.
- Активные URL, статусы, тела ответов и error contract не меняются.
- Из проекта не удаляются review requests, личный архив записей, material editor, S3/R2, SMTP, backup и
  storage cleanup.

## Пакет 1. Retired backend и зависимости

### Удаляемый код

- неиспользуемые Pydantic-схемы групп, назначений и submissions из `src/trainer/api/schemas.py`;
- пустые migration-boundary модули `api/routes/work.py` и `api/controllers/work.py`;
- `services/assignment_assets.py`: production-код его не импортирует, активный review workflow использует
  отдельный `services/review_assets.py`;
- retired query-функции групп, назначений и старых submissions из
  `infrastructure/database/queries/combined.py` и их re-export wrappers;
- `infrastructure/database/submissions.py` и `infrastructure/exports.py`: их единственные потребители —
  тесты retired workflow;
- тесты, которые проверяют только удалённые сервисы или экспорт, но не миграционную совместимость.

Перед каждым удалением выполняется `rg` по production-коду. Если символ нужен активному review-request
workflow, он переносится в модуль с актуальным именем и покрывается существующим контрактным тестом.

### Сохраняемая совместимость

`review_assets.py` сейчас использует `ASSIGNMENT_ASSET_DIR` как физический target root. Константа получает
актуальное логическое имя `REVIEW_ASSET_DIR`, но на этом этапе продолжает указывать на существующий каталог
`var/assignment-assets`. Это сохраняет доступ к уже записанным файлам без скрытой массовой миграции.

Колонки `assignment_keys_json` в cleanup jobs и legacy-таблицы не переименовываются: это изменение схемы,
а не удаление мёртвого runtime-кода. Их дальнейшая судьба оформляется отдельным ADR после истечения срока
хранения legacy-данных.

Compatibility-обработка retired URL в `main.py` остаётся: интеграционный тест фиксирует намеренный ответ
404 вместо 405 для старых клиентов. Её удаление потребует отдельного решения о жизненном цикле API.

### Зависимости

- `reportlab` удаляется из production requirements вместе с неиспользуемым PDF-export;
- `Pillow` переносится из `requirements.txt` в `requirements-dev.txt`, поскольку нужен импортёру банка,
  а не работающему приложению;
- `boto3`, Alembic, FastAPI и аудио-инструменты остаются.

## Пакет 2. Документация

Активные документы приводятся к принятому ADR 0004:

- SQLite — единственный поддерживаемый runtime database engine;
- PostgreSQL scale profile отсутствует;
- transcription worker удалён;
- `legacy/` удалён;
- актуальные operational commands перечисляются только при наличии соответствующих файлов и Compose-сервисов.

Исправляются `README.md`, `DEVELOPMENT.md`, `docs/architecture.md`, `docs/README.md`, `AGENTS.md`, `CLAUDE.md`,
`docs/agent-guidelines.md` и runbook-ссылки. Остальные Markdown-файлы проверяются поиском упомянутых
локальных путей; найденная ссылка на отсутствующий runtime-файл либо исправляется, либо остаётся только в
явно помеченном историческом архиве.

Исторические `docs/superpowers/plans/` и завершённые `docs/superpowers/specs/` не уничтожаются: они
переносятся под `docs/archive/superpowers/`. В активном `docs/README.md` остаётся одна ссылка на архив и
пояснение, что документы описывают прошлые состояния системы и не являются эксплуатационной инструкцией.
Текущая спецификация переносится в архив только после завершения всей работы.

## Пакет 3. Frontend

### CSS

`frontend/styles/base.css` очищается от правил, полностью перекрытых финальным unified-interface слоем.
Сохраняются design tokens, общие компоненты, runner, account и teacher styles. Страничные сетки продолжают
жить в `frontend/styles/pages/`.

Удаление выполняется небольшими группами селекторов. После каждой группы запускаются JS-тесты, а после
всего пакета — E2E и визуальная проверка. Цель — уменьшить каскад и дублирование, а не изменить дизайн.

### Элементы выбора

`frontend/js/shared/project-select.js` и связанные CSS удаляются. Обычные формы и фильтры используют
нативный `<select>`, который получает проектные цвета, размеры и `focus-visible` через CSS.

Карточный выбор материала на главной не зависит от этого polyfill и сохраняется. После удаления
проверяются keyboard navigation, disabled state, filters преподавателя и редактор материалов.

## Тесты и критерии приёмки

1. `make check` проходит после каждого из трёх пакетов.
2. `make test-e2e` проходит после frontend-пакета.
3. Coverage не поддерживается искусственно тестами удалённого кода и не падает ниже установленного порога.
4. Чистая и обновляемая SQLite-база проходят миграционные тесты; published revisions не изменены.
5. Существующие review-assets и записи доступны после обновления.
6. `requirements.txt` содержит только runtime-зависимости.
7. Активная документация не ссылается на отсутствующие runtime, worker, runbook или Compose-файл.
8. Главная, каталог, справочник, runner, account, teacher queue и material editor сохраняют текущий вид и
   keyboard behavior.

## Не входит в работу

- удаление legacy-таблиц и данных из пользовательских баз;
- изменение продуктовой модели регистрации или доступности вариантов;
- новый учебный режим, аналитика прогресса или обратная связь преподавателя;
- переход на frontend-фреймворк или TypeScript;
- изменение визуального дизайна.
