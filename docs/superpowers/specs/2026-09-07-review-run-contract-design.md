# Строгий контракт snapshot-а попытки в review request

## Цель и согласованный объём

Заменить свободный словарь `ReviewRequestCreate.run` на строгий snapshot завершённой
попытки Progress V2. Новый review request должен принимать только канонический
`CompletedProgressRun`, проверять его связь с выбранным вариантом и заданиями и
сохранять в `run_json` детерминированный JSON.

Это следующий вертикальный этап после внедрения Progress V2. Он меняет только
создание review request и повторно использует уже действующий контракт завершённой
попытки. Публичный путь, авторизация, остальные операции review request, схема
SQLite и существующие строки базы данных не меняются.

Пользователь согласовал:

- строгий контракт только для новых запросов на разбор;
- сохранение читаемости существующих legacy-строк `run_json` без фоновой миграции;
- повторное использование domain-модели и правил `CompletedProgressRun` вместо
  второй независимой реализации;
- обязательный статус `completed`;
- совпадение `run.variantId` с `ReviewRequestCreate.variantId`;
- выбор только заданий из `run.completedTasks`, при этом выбранные задания могут
  быть их подмножеством;
- удаление устаревшего лимита `run_too_large`, который недостижим для строгой
  ограниченной структуры.

## Текущее поведение и проблема

`ReviewRequestCreate.run` сейчас объявлен как `dict[str, Any]`. API проверяет
`kind`, `variantId` и `tasks`, но не структуру snapshot-а. Сервис сериализует любой
JSON-совместимый объект и отклоняет только результат больше 100 КБ. Поэтому в
`run_json` можно записать объект без идентификатора попытки, с другим вариантом,
незавершённым заданием или произвольными полями.

Frontend уже отправляет результат `getCompletedRun()`, то есть завершённую попытку
Progress V2. Свободный серверный контракт не даёт полезной совместимости для
текущего клиента, зато позволяет сохранить противоречивые данные и дублирует
неявное описание run между браузером, тестами и сервером.

Размер каждого строкового поля и массива строгого `CompletedRun` ограничен.
Следовательно, сериализованный документ заведомо значительно меньше 100 КБ, и
ветка `run_too_large` после строгой проверки становится недостижимой.

## Рассмотренные подходы

### Повторно использовать Progress V2 — выбран

`trainer.domain.progress` предоставляет публичные функции
`parse_completed_run()` и `completed_run_to_dict()` для разбора одного
`CompletedProgressRun` и его канонической сериализации. Review domain применяет к
этой модели собственные связи с `kind`, `tasks` и `variantId`. Transport-модель
использует существующую строгую Pydantic-схему `CompletedRun`.

Так сохраняется один источник правил для timestamps, режимов, состава заданий,
статуса и обязательных полей. Изменение не связывает domain с Pydantic или HTTP.

### Использовать только Pydantic-схему

Этот вариант проверил бы HTTP-вход, но сервис по-прежнему принимал бы произвольный
объект при прямом вызове. Канонизация и предметные связи оказались бы в controller
или transport validator. Подход отклонён, потому что прикладная граница должна
защищать инварианты независимо от HTTP.

### Создать отдельную review-run модель

Отдельная модель позволила бы менять snapshot независимо, но сейчас его поля и
семантика намеренно совпадают с `CompletedProgressRun`. Копия быстро разошлась бы
с Progress V2 и потребовала бы дублирующих fixtures. Подход отклонён как
преждевременное разделение контрактов.

## Контракт нового запроса

`ReviewRequestCreate.run` становится строгим `CompletedRun`. Он содержит ровно
следующие поля:

```json
{
  "id": "run-2026-09-07-001",
  "variantId": "open-2026",
  "variantLabel": "Открытый вариант 2026",
  "mode": "exam",
  "tasks": [1, 2, 3],
  "completedTasks": [1, 2, 3],
  "currentTask": 3,
  "phase": "answer",
  "fastMode": false,
  "startedAt": "2026-09-07T10:00:00.000Z",
  "status": "completed",
  "completedAt": "2026-09-07T10:30:00.000Z",
  "recordingsCount": 7
}
```

Структурные правила полностью совпадают с Progress V2:

- неизвестные и отсутствующие поля запрещены;
- строки, integer и boolean не приводятся из других типов;
- `mode` определяет допустимый состав `tasks`;
- `completedTasks` является уникальным подмножеством `tasks`;
- `currentTask` входит в `tasks`;
- timestamps имеют timezone-aware RFC 3339 формат, а `completedAt` не раньше
  `startedAt`;
- `recordingsCount` — целое число от 0 до 100;
- для `status=completed` список `completedTasks` равен `tasks`.

Review request добавляет три межполевых правила:

1. `run.status` равен `completed`; прерванную попытку отправить нельзя.
2. `run.variantId` равен корневому `variantId` запроса.
3. Все выбранные `tasks` входят в `run.completedTasks`.

Для `kind=task` сохраняется требование выбрать ровно одно задание. Для
`kind=attempt` можно выбрать одно или несколько завершённых заданий. Выбранные
`tasks` не обязаны равняться всем заданиям попытки: frontend отправляет только те
задания, для которых пользователь подготовил полный комплект записей.

Порядок `tasks`, `completedTasks` и выбранных заданий канонизируется по
возрастанию. Проверка и сериализация не изменяют входной объект.

## Компоненты и границы

### Domain progress

`src/trainer/domain/progress.py` открывает публичные функции для строгого разбора
одного завершённого запуска и преобразования `CompletedProgressRun` в
канонический словарь. Реализация переиспользует действующие внутренние правила;
новая параллельная схема не создаётся.

Ошибки структуры продолжают выражаться через `ProgressValidationError`. Domain
остаётся независимым от API, Pydantic, service и infrastructure.

### Domain review requests

`src/trainer/domain/review_requests.py` получает операцию проверки полного набора
данных создания: `kind`, выбранных `tasks`, корневого `variantId` и run. Она:

1. применяет существующие правила selection;
2. разбирает run через публичную границу Progress V2;
3. проверяет статус и межполевые связи;
4. возвращает нормализованный selection и типизированный
   `CompletedProgressRun`.

Review domain владеет только связями между частями запроса. Он не дублирует
валидацию timestamps, полей запуска или режима.

### API schema и controller

В `src/trainer/api/schemas.py` поле `ReviewRequestCreate.run` использует строгую
модель `CompletedRun` вместо `dict[str, Any]`. Model validator запроса передаёт
словарь run в `parse_completed_run()`, поэтому внутренние domain-инварианты,
которые невозможно выразить ограничениями отдельных полей Pydantic, также дают
transport-ошибку 422. Он намеренно не проверяет связь run с корневыми
`variantId` и `tasks`: это предметные правила review domain с ответом 400.

Controller преобразует Pydantic-модель в обычный JSON-совместимый словарь и
передаёт его сервису. HTTP-слой не формирует канонический JSON и не решает
предметные связи.

### ReviewRequestService

`ReviewRequestService.create()` на своей публичной границе повторно вызывает
полную domain-проверку. Это защищает прямые вызовы сервиса и не полагается на то,
что данные обязательно пришли из FastAPI.

После успешной проверки сервис сериализует только канонический словарь run с
`ensure_ascii=False` и компактными separators. Именно эта строка передаётся в
`session.create_request()`. Получение материала, snapshot assets, transaction,
audit и cleanup остаются без изменений.

Валидация run и всех его связей завершается до открытия repository transaction,
поиска материала, копирования assets и записи данных. Ошибочный запрос не имеет
побочных эффектов.

## Поток данных

1. FastAPI проверяет JSON по `ReviewRequestCreate`, включая строгую структуру
   `CompletedRun`.
2. Controller переводит `run` в обычный словарь без изменения значений.
3. Service передаёт весь набор создания в review domain.
4. Progress domain возвращает типизированный канонический
   `CompletedProgressRun`.
5. Review domain проверяет статус, вариант и выбранные завершённые задания.
6. Service сериализует каноническое представление run.
7. Только затем начинается прежний сценарий material snapshot и transaction.

Повторная domain-проверка между API и persistence намеренна: schema даёт точные
transport-ошибки клиенту, а service сохраняет независимую прикладную границу.

## Ошибки

Неверная структура `run` на HTTP-границе возвращает стандартный HTTP 422 с code
`request_validation_failed`. Сюда относятся отсутствующие или лишние поля,
неверные строгие типы, недопустимые enum, timestamps и внутренние инварианты
`CompletedRun`.

Значение `status=interrupted` само по себе соответствует общей структуре
`CompletedRun`, поэтому относится не к transport-ошибке, а к предметному запрету
review request ниже.

Корректно сформированный run, который не соответствует контексту review request,
возвращает HTTP 400 с существующим code `invalid_request` и конкретным русским
сообщением. Это включает:

- попытка не завершена;
- вариант попытки не совпадает с выбранным вариантом;
- выбрано задание, отсутствующее среди завершённых.

Прямой вызов service с неверной структурой также возвращает
`ReviewRequestError("invalid_request")`; transport-specific 422 существует только
на Pydantic-границе. Ни один ошибочный сценарий не исправляет вход молча и не
создаёт request, items, audit или snapshot assets.

Причина `run_too_large`, её controller mapping и отдельный unit-тест удаляются.
Отдельный byte-size guard не заменяется: максимальный размер строгой модели уже
ограничен длинами её полей и массивов.

## Совместимость и хранение

Новые запросы всегда сохраняют канонический `CompletedProgressRun`. SQLite-колонка
`review_requests.run_json` и миграции не меняются.

Существующие строки могут содержать прежний свободный JSON. Они остаются
неизменными: нет startup migration, фоновой перезаписи или lazy write. Текущие
list/detail ответы не декодируют и не возвращают `run_json`, поэтому legacy-строки
не мешают действующим пользовательским и учительским сценариям. Если чтение run
появится в будущем, для него потребуется отдельное явное compatibility-решение.

Frontend не меняет payload: текущий `getCompletedRun()` уже формирует структуру,
совместимую с Progress V2. Прямые API-тесты и фикстуры с минимальными объектами
вроде `{}` или `{"elapsed": 15}` обновляются до полного канонического run.

## Тестирование

Работа выполняется по TDD и проверяется на каждой границе.

### Domain unit tests

- публичный разбор одного `CompletedProgressRun` принимает корректный объект,
  нормализует timestamps и сортирует списки;
- сериализация возвращает только канонические поля и не меняет вход;
- review validation принимает допустимое подмножество завершённых заданий;
- отклоняются `interrupted`, несовпадающий `variantId` и незавершённое выбранное
  задание;
- структурные ошибки Progress V2 преобразуются review domain в понятную ошибку
  создания.

### Service unit tests

- `create()` сохраняет канонический JSON, а не исходный порядок/формат;
- прямой неверный ввод отклоняется до transaction, material lookup, assets и
  persistence;
- входной словарь не мутирует;
- существующие успешные material snapshot, audit и cleanup сценарии сохраняются;
- удаляется тест произвольного объекта больше 100 КБ.

### API integration tests

- неверная структура run даёт `422 request_validation_failed`;
- прерванная попытка и нарушения связей дают `400 invalid_request`;
- корректный полный run создаёт review request без изменения response envelope;
- существующая legacy-строка в базе остаётся доступна через действующие list/detail
  сценарии без миграции;
- текущие create/upload/complete flows работают с полным canonical fixture.

### Browser и итоговая проверка

JavaScript- и Playwright-тесты подтверждают, что текущий frontend payload проходит
новый контракт и пользователь может создать и отправить заявку. Обязательные
финальные команды:

```bash
make check
make test-e2e
```

## Вне объёма

- строгий контракт `content` материалов и их task snapshots;
- изменение UI создания заявки или набора требуемых аудиозаписей;
- возврат run в list/detail API;
- миграция или удаление legacy `run_json`;
- изменение таблиц, индексов или Alembic revisions;
- отдельное версионирование review snapshot-а;
- произвольный новый лимит размера тела HTTP-запроса.

## Критерий готовности

Каждый новый review request содержит канонический snapshot завершённой попытки,
согласованный с вариантом и выбранными заданиями. Неверный ввод отклоняется до
побочных эффектов с предсказуемым HTTP-ответом, существующие данные продолжают
работать без миграции, а `make check` и `make test-e2e` завершаются успешно.
