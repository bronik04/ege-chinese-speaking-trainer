# Единая история ученика

## Цель и согласованный объём

Заменить разрозненные списки попыток, личных аудиозаписей и заявок на разбор одной
страницей `История`. Основной объект страницы — попытка тренировки. Связанные с ней
аудиозаписи, сроки их хранения и результаты преподавателя раскрываются внутри той
же карточки.

Страница предназначена для гостя и ученика. Гость видит локальные попытки и
приглашение войти. Ученик видит объединённую историю аккаунта. Очередь и история
преподавателя остаются в кабинете преподавателя и не меняются.

В объём также входит удаление старого модального окна истории, блока `Мои разборы`
на главной и кнопки `Очистить историю`. Новых таблиц, миграций или отдельного
серверного агрегатора истории не создаётся.

## Текущее поведение и проблема

Один пользовательский сценарий сейчас разделён между тремя местами:

- локальные завершённые и прерванные попытки находятся в модальном окне истории;
- личные аудиозаписи выводятся отдельным списком в том же окне;
- заявки на разбор выводятся отдельным блоком на главной странице.

Пользователь вынужден сопоставлять записи и оценки с попыткой по названию материала
и дате. Кнопка очистки удаляет попытки из документа прогресса, но сохраняет аудио и
заявки, поэтому дополнительно разрушает связь между списками. На уровне данных уже
есть общий идентификатор попытки: `runId` хранится в прогрессе, личных записях и
каноническом снимке попытки внутри review request.

## Рассмотренные подходы

### Объединение на странице по `runId` — выбран

Страница получает существующий документ прогресса, личные записи и заявки на
разбор, затем чистая frontend-модель объединяет их по `runId`. Review request API
добавляет этот идентификатор из уже сохранённого `run_json`.

Подход не дублирует данные, не создаёт новую серверную зависимость между сервисами
и использует существующие правила авторизации каждого источника.

### Новый серверный endpoint истории

Сервер мог бы возвращать уже собранную хронологию. Это упрощает страницу, но новый
application service должен знать внутреннее JSON-представление прогресса,
репозитории личных записей и review requests. Ради одного представления появляется
нежелательная связь трёх прикладных областей.

### Отдельная таблица событий

Запись каждого завершения, загрузки и проверки в activity feed даёт гибкую ленту,
но требует миграции, обратного заполнения и синхронизации с исходными таблицами.
Это дублирование существующих данных не оправдано текущей задачей.

## Архитектура и компоненты

~~~text
history.html
  -> history-page.js            orchestration и защита от смены аккаунта
       -> progress.js           локальный прогресс, валидация и merge
       -> существующие API      auth, progress, personal recordings, reviews
       -> history-model.js      чистое объединение по runId
       -> history-view.js       безопасная разметка хронологии

student review request API
  -> ReviewRequestService
       -> review request repository
            -> SQLite query читает run_json и публикует только runId
~~~

`history-model.js` не обращается к DOM, storage или сети. Он принимает три массива
и возвращает канонические элементы хронологии. `history-view.js` отвечает только
за текст, экранирование и разметку. `history-page.js` определяет пользователя,
загружает доступные источники, показывает частичные ошибки и подключает действия.

Существующие backend-границы не объединяются: каждый API по-прежнему получает
данные через свой сервис и применяет собственные правила доступа.

## Контракт `runId` для заявок на разбор

`GET /api/student/review-requests` добавляет в каждый элемент поле:

~~~json
{"runId": "run-123"}
~~~

Значение извлекается из `run_json`, который сохраняется при создании заявки после
валидации канонического completed run. Остальные поля и правила сокрытия баллов до
проверки не меняются.

Для совместимости с повреждённой исторической строкой JSON-декодирование или
отсутствующий/некорректный `id` дают `runId: null`, а не ошибку всего списка.
Frontend создаёт для такой заявки отдельный восстановленный элемент и никогда не
объединяет два элемента с пустым идентификатором. Ответы teacher API, поведение и
разметка кабинета преподавателя не меняются.

## Загрузка прогресса и изоляция аккаунтов

Страница сначала выполняет `GET /api/auth/me`.

### Гость

При ответе 401 читается и валидируется только гостевой документ прогресса из
localStorage. Серверные endpoints прогресса, записей и заявок не вызываются.
Страница показывает приглашение войти, объясняющее синхронизацию и шестимесячное
хранение аудио.

### Ученик

Страница читает account-scoped локальный прогресс и `GET /api/progress`, объединяет
их существующей функцией `mergeProgress`, сохраняет канонический результат в
account-scoped localStorage и отправляет его через существующий `PUT /api/progress`.
Это повторяет текущий контракт синхронизации тренажёра, не создавая нового
endpoint. Затем страница параллельно запрашивает личные записи и review requests.

Каждая загрузка получает generation token и ID пользователя. Результат применяется
только пока оба значения актуальны. Ответ предыдущего аккаунта после выхода или
смены пользователя не может попасть на экран.

### Преподаватель

Аккаунт преподавателя не загружает ученические progress, recordings или review
requests. Страница показывает краткое объяснение и ссылку в существующий кабинет
преподавателя. Локальная гостевая история к аккаунту преподавателя не подмешивается.

## Правила объединения

Канонический элемент содержит:

- стабильный `runId` или уникальный synthetic key для несвязанного legacy-объекта;
- данные попытки, если они доступны;
- массив личных записей;
- массив заявок на разбор;
- вычисленную дату сортировки.

Алгоритм:

1. Создать по одному элементу для каждой попытки прогресса, ключом служит её `id`.
2. Добавить каждую личную запись в элемент с тем же `runId`; при отсутствии
   попытки создать восстановленный элемент из `variantId`, task и `createdAt`.
3. Добавить каждую заявку с непустым `runId` в соответствующий элемент; при
   отсутствии попытки создать восстановленный элемент из `variantId`, tasks и
   `submittedAt`.
4. Для заявки с `runId: null` создать отдельный ключ `review:<requestId>`.
5. Отсортировать элементы от новых к старым. Используется `completedAt` или
   `startedAt` попытки, а для восстановленного элемента — наиболее поздняя дата
   записи или заявки. Равные даты разрешаются стабильным ключом.

Все записи и все заявки сохраняются в массивах, даже если один run породил
несколько review requests. В свёрнутой карточке показывается состояние самой новой
заявки; полный список виден после раскрытия.

## Страница и навигация

Во всех публичных шапках появляется ссылка `История`. Кнопка `История` в личном
кабинете заменяется обычной ссылкой на ту же страницу. Ссылка доступна гостю:
история без аккаунта является поддерживаемым сценарием.

Новая страница следует существующей визуальной системе каталога и справочника:
общая шапка, светлый фон, бордовые заголовки, золотые акценты и одноколоночная
хронология. Вверху находятся заголовок `Моя история`, краткое число попыток и
статус загрузки.

Каждый элемент реализуется нативной парой `<details>/<summary>`:

- в summary находятся материал, дата, тип тренировки, состояние попытки,
  количество записей и состояние самой новой заявки;
- в раскрытой области записи группируются по заданиям, выводятся audio controls и
  дата автоматического удаления;
- заявки показывают выбранные задания, дату, состояние и итоговый балл только
  после проверки;
- незавершённая загрузка сохраняет существующее действие удаления этой загрузки;
- если сведения о попытке отсутствуют, карточка явно помечается как восстановленная
  из архива и не выдумывает состояние `Завершено` или `Прервано`.

Карточки управляются мышью и клавиатурой без отдельного JavaScript accordion.
Фокус заметен, элементы управления имеют не менее 44 пикселей по короткой стороне,
а мобильная версия остаётся в одну колонку без горизонтальной прокрутки.

## Удаляемое поведение

С главной страницы удаляются:

- `studentReviewRequestsPanel` и его список;
- `progressModal`, отдельные history/recordings lists и пояснение очистки;
- обработчики открытия и закрытия progress modal;
- `clearHistory`, подтверждение и кнопка `Очистить историю`;
- frontend-rendering, который отдельно строит старые списки.

Фоновое сохранение личных записей после завершения тренировки и отправка заявки на
разбор остаются. Контроллеры этих сценариев перестают рендерить архивы на главной;
просмотр и удаление незавершённой заявки принадлежат новой странице истории.

## Ошибки и неполные данные

- Некорректный локальный прогресс обрабатывается существующей безопасной загрузкой
  и не ломает страницу.
- Недоступный серверный progress оставляет валидную account-scoped локальную копию.
- Если `GET /api/auth/me` недоступен по сетевой причине, страница не предполагает
  личность пользователя, показывает только гостевую локальную историю и сообщение
  о невозможности проверить вход.
- Ошибка personal recordings или review requests не скрывает попытки и данные
  второго источника. Возле соответствующей части показывается краткое сообщение и
  кнопка повторной загрузки.
- Ответ 401 во время загрузки переводит страницу в гостевое состояние и очищает
  уже подготовленные account-scoped данные из DOM.
- Удаление незавершённой заявки требует существующего подтверждённого API-вызова;
  после успеха модель перечитывается. Ошибка оставляет карточку и сообщает о
  невозможности удаления.
- Идентификаторы и все сетевые строки экранируются перед включением в HTML. Audio
  URL формируются только существующими API helpers по числовым ID.

## Документация

README описывает `Историю` как единый экран попыток, аудио и разборов. Упоминания
отдельного личного архива и старого пути через модальное окно обновляются. Правила
хранения записей и эксплуатационные runbooks не меняются.

## Проверка

- Backend unit/integration tests: канонический `runId`, `null` для повреждённого
  `run_json`, сохранение прежних полей и сокрытие баллов queued-заявки.
- JavaScript unit tests: объединение трёх источников, несколько заявок одного run,
  восстановленные элементы, отдельные null-ID заявки, стабильная сортировка,
  безопасное экранирование и формирование summary/detail.
- Browser tests, гость: ссылка в навигации, только локальные попытки, приглашение
  войти, отсутствие серверных student-запросов и отсутствие кнопки очистки.
- Browser tests, ученик: одна карточка связывает попытку, audio с датой удаления и
  review status/score; незавершённую загрузку можно удалить.
- Browser tests, устойчивость: перехваченный сбой одного источника сохраняет
  остальные карточки и допускает повтор; поздний ответ другого аккаунта не
  отображается.
- Accessibility/responsive tests: `<details>/<summary>`, клавиатура, видимый focus,
  44px controls и отсутствие горизонтального overflow на мобильном viewport.
- Regression tests подтверждают отсутствие старого блока на главной, progress
  modal и его обработчиков.
- Полная проверка: `make check` и `make test-e2e`.

## Вне объёма

- кабинет, очередь, фильтры и история преподавателя;
- сроки хранения, storage keys и правила доступа к аудио;
- критерии, расчёт и редактирование оценок;
- новые таблицы или миграции базы данных;
- удаление отдельной завершённой попытки, сохранённой записи или проверенной заявки;
- аналитические графики, серии занятий и рекомендации по прогрессу;
- изменение формата progress document V2.
