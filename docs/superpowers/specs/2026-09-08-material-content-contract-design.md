# Строгий контракт содержимого авторских материалов

## Цель и согласованный объём

Заменить свободный словарь `MaterialRequest.content` на строгий контракт
редактируемого черновика. Новые запросы создания и изменения материала должны
проверять набор заданий, поля, типы и фиксированную длину списков до открытия
транзакции и сохранять только каноническое представление.

Это следующий вертикальный этап после Progress V2 и строгого snapshot-а review
request. Изменение затрагивает API создания и изменения материалов, domain-правила
черновика, сервисную границу и сбор payload в браузерном редакторе. Публикация,
официальные JSON-варианты, схема SQLite и чтение существующих строк не меняются.

Пользователь согласовал:

- типизированные модели черновиков для заданий 1, 2 и 3;
- строгую проверку всех новых create/update запросов;
- возможность сохранять структурно корректный, но ещё незаполненный черновик;
- сохранение прежних содержательных проверок при публикации;
- чтение существующих legacy-строк без миграции и фоновой перезаписи;
- обязательное соответствие `kind`, `taskNumber` и ключей `content`;
- удаление отдельного лимита произвольного `content` в 150 КБ после введения
  ограничений каждого поля.

## Текущее поведение и проблема

`MaterialRequest.content` сейчас объявлен как `dict[str, Any]`. Pydantic проверяет
только корневые metadata-поля, а сервис `_normalize()` подтверждает лишь, что
`content` является словарём и его JSON-представление не превышает 150 КБ. Поэтому
create/update принимают неизвестные задания, лишние поля, неверные типы и списки
произвольной длины. Ошибка обнаруживается только при публикации, а часть лишних
данных может до этого храниться в SQLite.

Domain-функции `build_task()` и `build_content()` уже описывают содержательную
полноту опубликованного материала. Их нельзя напрямую применить к create/update:
редактор намеренно сохраняет пустые строки и незагруженные изображения как
черновик. Нужен отдельный структурный контракт черновика, который не дублирует
проверку готовности к публикации.

После публикации в `content_json` находятся также фиксированные поля экзамена из
`EXAM_SPEC`: таймеры, заголовки, инструкции и начало ответа. Текущий frontend
загружает их в локальный `content` и из-за spread-операций может отправить обратно
при следующем редактировании. Строгий запрос не должен принимать эти производные
поля: браузерный редактор будет собирать payload только из редактируемых значений.

## Рассмотренные подходы

### Domain-нормализатор и типизированные API-модели — выбран

Domain получает единый нормализатор структуры черновика. API описывает ту же
форму вложенными Pydantic-моделями и вызывает domain-нормализатор для проверки
связи корневых полей. Сервис повторяет нормализацию на собственной границе и
передаёт repository уже канонический словарь.

Так OpenAPI показывает реальный payload, HTTP-клиент получает точный ответ 422, а
прямой вызов сервиса не может обойти инварианты. Domain не зависит от Pydantic,
HTTP или SQLite.

### Только ручной валидатор словаря

Можно оставить `dict[str, Any]` и проверять его одной domain-функцией. Это
защитило бы persistence, но OpenAPI по-прежнему обещал бы произвольный JSON, а
ошибки отдельных полей были бы менее точными. Подход отклонён.

### Отдельные endpoints для трёх заданий

Разные запросы для полного варианта и каждого номера задания дали бы максимально
явные контракты, но потребовали бы менять маршруты, редактор и клиентскую модель
без пользовательской пользы. Подход отклонён как избыточный.

## Контракт черновика

Все вложенные модели используют строгие типы и запрещают неизвестные поля. Пустая
строка допустима, но максимальная длина каждого значения ограничена. Значения не
приводятся к строкам и не обрезаются автоматически; нормализатор сохраняет
переданный текст без изменения.

### Задание 1

```json
{
  "situation": "",
  "banner": "",
  "questions": ["", "", "", "", ""],
  "image": "",
  "imageAlt": ""
}
```

- `situation`: строка до 1500 символов;
- `banner`: строка до 300 символов;
- `questions`: ровно пять строк до 300 символов каждая;
- `image`: строка до 500 символов;
- `imageAlt`: строка до 300 символов.

### Задание 2

```json
{
  "images": ["", "", ""]
}
```

`images` содержит ровно три строки до 500 символов каждая.

### Задание 3

```json
{
  "title": "",
  "images": ["", ""],
  "imageLabels": ["", ""]
}
```

- `title`: строка до 150 символов;
- `images`: ровно две строки до 500 символов каждая;
- `imageLabels`: ровно две строки до 100 символов каждая.

Корневой `content` всегда является объектом с числовыми строковыми ключами:

- `kind=full`: обязательны ровно ключи `1`, `2`, `3`, а `taskNumber` равен
  `null` или опущен, как разрешает текущий корневой контракт;
- `kind=task`: обязателен ровно один ключ, совпадающий с `taskNumber`, а
  `taskNumber` входит в `1..3`;
- неизвестные ключи, пропущенное задание, прямое содержимое задания без внешнего
  ключа и несовпадающий номер запрещены.

Нормализатор возвращает новый словарь в порядке заданий и в фиксированном порядке
полей. Он не изменяет вход и не переносит в результат неизвестные значения.

## Разделение черновика и публикации

Структурная проверка create/update не требует непустых строк. Это сохраняет
главное свойство редактора: черновик можно записать до загрузки изображений и до
заполнения всех полей.

`build_content()` остаётся границей публикации. Она:

- требует содержательные минимальные длины;
- проверяет точное количество вопросов, изображений и подписей;
- добавляет фиксированные значения `EXAM_SPEC`;
- проверяет допустимую форму image URL через `material_asset_ids()`;
- сохраняет существующий `material_incomplete` для незавершённого материала.

Производные поля `prepSeconds`, `answerSeconds`, `lead`, `prompts`, `starter` и
фиксированный `title` задания 1 или 2 никогда не входят в write-контракт
черновика. После открытия ранее опубликованного материала frontend извлекает
только редактируемые поля и при сохранении создаёт чистый draft payload.

## Компоненты и границы

### Domain materials

`src/trainer/domain/materials.py` получает отдельную ошибку структурного контракта
и публичную функцию нормализации draft content. Она проверяет только JSON-форму,
строгие типы, максимальные длины, cardinality и связь `kind/task_number` с
ключами. Функции публикации продолжают отвечать за заполненность и asset URL.

Структурный нормализатор не использует Pydantic и не знает об HTTP. Его можно
вызвать из API-validator, service или unit-теста.

### API schema и controller

`src/trainer/api/schemas.py` получает строгие вложенные модели трёх заданий и
контейнер `MaterialDraftContent` с alias-ключами `1`, `2`, `3`. Model validator
`MaterialRequest` передаёт сериализованный content вместе с `kind` и
`taskNumber` в domain-нормализатор.

Ошибки формы и связей возникают на Pydantic-границе. Controller только переводит
проверенную модель в обычный JSON-совместимый словарь и формирует
`MaterialRequestData`; он не повторяет правила контракта.

Корневые metadata-правила `slug`, `title`, `year` и `source` остаются в текущем
объёме. Этап намеренно ужесточает `content` и его связь с `kind/taskNumber`, но не
меняет нормализацию остальных полей.

### MaterialService и repository

`MaterialService._normalize()` повторно вызывает domain-нормализатор до
transaction. Полученный новый словарь записывается в нормализованный
`MaterialRequestData`; исходный объект не меняется. Прямой вызов service с
неверной структурой преобразуется в `MaterialError("invalid_metadata")` и не
обращается к repository.

Repository и SQLite-схема не получают новых правил. Они сериализуют уже
канонический словарь тем же способом, что и сейчас. После публикации repository
по-прежнему сохраняет обогащённый `build_content()` результат.

Отдельная проверка `len(json.dumps(content)) > 150_000` удаляется. Строгие
максимумы строк и фиксированные размеры списков дают существенно меньшую верхнюю
границу. Общий middleware-лимит HTTP body продолжает защищать транспорт.

### Frontend editor

`frontend/js/materials/material-editor.js` перестаёт расширять загруженные task
objects через spread. `collectContent()` явно создаёт объекты только из пяти
полей задания 1, одного поля задания 2 и трёх полей задания 3. Загруженные image
URL сохраняются, а производные и неизвестные поля из legacy/published content не
попадают в новый запрос.

Для отдельного задания функция возвращает только выбранный ключ; для полного
варианта — все три ключа.

## Поток данных

1. Редактор собирает только редактируемые поля текущего материала.
2. Pydantic проверяет вложенные типы, поля и длины списков.
3. Validator корневого запроса проверяет связь `kind`, `taskNumber` и ключей через
   domain-нормализатор.
4. Controller преобразует модели в обычные словари.
5. Service повторно нормализует структуру до любых repository-вызовов.
6. Repository сохраняет канонический черновик.
7. При публикации `build_content()` проверяет полноту и добавляет `EXAM_SPEC`.

Повторная проверка между API и persistence намеренна: API отвечает за точные
transport-ошибки, service — за независимую прикладную границу.

## Ошибки

HTTP create/update возвращает стандартный `422 request_validation_failed`, если:

- `content` не является объектом;
- поле отсутствует, лишнее или имеет неверный строгий тип;
- список имеет неверную длину;
- ключи заданий не соответствуют `kind` и `taskNumber`;
- `kind=full` содержит ненулевой `taskNumber`;
- строка превышает максимальную длину.

Прямой вызов service с теми же нарушениями возвращает существующий HTTP-neutral
`MaterialError("invalid_metadata", message)`. Controller продолжает отображать
его в `400 invalid_material`, но обычный HTTP-запрос до сервиса не дойдёт.

Структурно корректный пустой черновик создаётся и обновляется успешно. Его
публикация возвращает прежний `400 material_incomplete` с конкретным сообщением
от `build_content()`.

Ошибки slug conflict, доступа, принадлежности asset, изображения и storage не
меняются.

## Совместимость и хранение

Новые create/update запросы сохраняют только канонический draft content.
Публичные маршруты и response envelopes не меняются. Миграция БД не требуется.

Существующие строки `materials.content_json` могут содержать прежний свободный
JSON или обогащённый опубликованный content. `detail()` продолжает декодировать и
возвращать их без строгой повторной проверки, поэтому доступные legacy-материалы
не исчезают и не переписываются при чтении.

При явном сохранении старого материала действует новый write-контракт. Обновлённый
frontend удаляет известные производные и неизвестные поля из payload. Если
внешний клиент отправит старую форму напрямую, API вернёт 422; автоматическое
исправление произвольного legacy JSON не выполняется.

Официальные файлы `content/variants/*.json` не являются входом
`MaterialRequest` и остаются под существующей отдельной схемой в
`scripts.validate_content`.

## Тестирование

Работа выполняется по TDD и проверяется на каждой границе.

### Domain unit tests

- каждый из трёх draft task принимается с пустыми строками и канонизируется;
- full content требует ровно задания 1–3;
- single-task content требует ровно выбранный ключ;
- неверные типы, лишние/пропущенные поля, неправильные длины списков и слишком
  длинные строки отклоняются;
- нормализация не изменяет вход.

### Service unit tests

- create/update сохраняют канонический словарь без неизвестных полей;
- неверная структура отклоняется до transaction;
- неполный структурно корректный черновик принимается;
- публикация продолжает отклонять незаполненный материал;
- устаревший тест произвольного объекта больше 150 КБ удаляется.

### API integration tests

- нарушения вложенной схемы и связей дают `422 request_validation_failed`;
- каждый допустимый single-task и полный draft можно сохранить;
- незаполненный draft нельзя опубликовать;
- корректный материал публикуется с прежними фиксированными полями;
- вручную добавленная legacy-строка читается и не изменяется;
- каноническое содержимое проверяется непосредственно в SQLite.

### JavaScript и browser tests

- unit test `collectContent()` или выделенного чистого helper подтверждает удаление
  производных и неизвестных полей;
- Playwright проходит путь создания, загрузки изображений, сохранения и публикации
  отдельного задания;
- редактирование ранее опубликованного материала не отправляет производные поля.

Финальные обязательные команды:

```bash
make check
make test-e2e
```

## Вне объёма

- изменение правил и текстов `EXAM_SPEC`;
- новая версия формата официальных вариантов;
- миграция, исправление или удаление legacy `content_json`;
- строгая проверка старых строк при чтении;
- изменение схемы SQLite или Alembic revisions;
- новые endpoints или изменение разрешений редактора;
- переработка UI редактора за пределами безопасной сборки payload;
- изменение общего лимита HTTP body.

## Критерий готовности

Каждый новый create/update запрос материала содержит только структурно корректный
канонический draft content, согласованный с типом и номером задания. Пустые
черновики сохраняются, а полнота проверяется при публикации. Ошибочный ввод не
доходит до persistence, старые данные читаются без миграции, и свежие
`make check` и `make test-e2e` завершаются успешно.
