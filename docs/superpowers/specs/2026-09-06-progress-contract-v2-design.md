# Строгий контракт прогресса V2

## Цель и согласованный объём

Заменить слабо проверяемый документ прогресса версии 1 на явный, версионированный
контракт V2. Сервер, browser storage и синхронизация должны работать с одной
канонической структурой, а существующий прогресс V1 — автоматически переноситься
без потери корректных попыток.

Это отдельный вертикальный этап только для прогресса. Строгие контракты snapshot-а
review request и `content` материалов будут выполнены позднее. Схема SQLite и
HTTP-пути `GET /api/progress`, `PUT /api/progress` не меняются.

Пользователь согласовал:

- автоматическую нормализацию старых документов V1 вместо сброса или требования
  ручного действия;
- нейтральный domain-нормализатор и строгие Pydantic-модели на HTTP-границе;
- отдельную реализацию progress-контракта до `run` и `content`;
- миграцию как серверных документов, так и guest/per-user ключей `localStorage`.

## Текущее поведение и проблема

Серверная schema принимает `progress: dict[str, Any]`, а domain проверяет только
`version == 1`, тип `runs` и предел в 200 элементов. Вложенные поля, типы, связи
между заданиями и timestamps не определены. Из-за Python-сравнения значениями
версии также ошибочно считаются `true` и `1.0`.

Frontend неявно определяет реальную структуру документа:

- `settings.lastVariant` и `settings.fastMode`;
- активный запуск с вариантом, режимом, заданиями, фазой и временем старта;
- завершённые или прерванные попытки с числом записей и временем завершения;
- клиентский `updatedAt`, используемый при объединении локальной и серверной копий.

Документ хранится под ключами `egeChineseProgressV1` и
`egeChineseProgressV1:user:<id>`. Сейчас повреждённый вложенный элемент может
пройти серверную проверку, а повреждение корня приводит к молчаливому сбросу
локального прогресса. Контракт Python и JavaScript не зафиксирован общими
миграционными примерами.

Завершённая попытка используется не только историей: frontend передаёт её как
snapshot при создании review request. Поэтому V2 сохраняет совместимые поля
запуска; ужесточение отдельного review-контракта не входит в этот этап.

## Рассмотренные подходы

### Domain-нормализатор и строгая transport schema — выбран

Domain владеет версией, канонической моделью, инвариантами и преобразованием V1 в
V2. API описывает V2 строгими Pydantic-моделями и переводит transport-данные в
нейтральное представление. Frontend реализует то же преобразование для локальных
данных, а общие JSON-fixtures проверяют одинаковый результат двух реализаций.

Такой подход не связывает бизнес-правила с HTTP или Pydantic, даёт строгий новый
контракт и одновременно позволяет безопасно прочитать исторические документы.

### Проверять только Pydantic-моделями

Вариант короче, но переносит миграцию и канонизацию в API. Сервис не сможет
независимо нормализовать документ, прочитанный из repository, а domain станет
зависеть от transport-деталей. Подход отклонён.

### Оставить свободный словарь и добавить ручные проверки

Это сохраняет неоднозначность схемы и допускает расхождение сериализации между
слоями. Ошибки будут находиться только во время выполнения. Подход отклонён.

## Канонический документ V2

Канонический JSON имеет только следующие корневые поля:

```json
{
  "version": 2,
  "updatedAt": "2026-09-06T10:15:30.000Z",
  "settings": {
    "lastVariant": "open-2026",
    "fastMode": false
  },
  "runs": [],
  "activeRun": null
}
```

Неизвестные поля в новом V2 запрещены на всех уровнях. `version` — строго целое
число `2`: boolean, float и строка не приводятся к integer. Временные отметки —
валидные timezone-aware RFC 3339 значения; при нормализации они сериализуются в
UTC с суффиксом `Z` и миллисекундами.

### Settings

- `lastVariant`: `null` или строка длиной 1–80 символов;
- `fastMode`: строго boolean.

### Общие поля запуска

- `id`: непустая строка длиной до 120 символов;
- `variantId`: строка длиной 1–80 символов;
- `variantLabel`: строка длиной 1–160 символов;
- `mode`: только `exam` или `practice`;
- `tasks`: от одного до трёх уникальных целых номеров из `1`, `2`, `3`;
- `completedTasks`: уникальные номера из `tasks`;
- `currentTask`: один из `tasks`;
- `phase`: только `idle`, `prep` или `answer`;
- `fastMode`: строго boolean;
- `startedAt`: timezone-aware RFC 3339 timestamp.

Порядок `tasks` и `completedTasks` канонизируется по возрастанию. Для `exam`
ожидаются задания `[1, 2, 3]`; для `practice` — ровно одно задание. Это отражает
единственные сценарии создания запуска в текущем frontend.

### Активный запуск

`activeRun` равен `null` или содержит только общие поля запуска. Его
`completedTasks` может быть пустым или частичным. `currentTask` остаётся заданием,
на котором продолжится сценарий.

### Завершённая попытка

Каждый элемент `runs` содержит общие поля запуска и дополнительно:

- `status`: только `completed` или `interrupted`;
- `completedAt`: timezone-aware RFC 3339 timestamp не раньше `startedAt`;
- `recordingsCount`: целое число от 0 до 100.

Поля `phase`, `currentTask` и `fastMode` остаются в завершённой попытке для
совместимости истории и snapshot-а review request. Для `status=completed`
`completedTasks` равен `tasks`; для `status=interrupted` допускается его подмножество.

Каноническая история содержит не более 100 попыток. Порядок входной истории
сохраняется: frontend уже хранит новые попытки первыми. Строгий V2 отклоняет
дублирующиеся run ID. Legacy migration удаляет дубликаты с сохранением первого
валидного элемента.

## Domain-модель и нормализация

`src/trainer/domain/progress.py` содержит нейтральные immutable-модели V2,
парсер/валидатор V2, мигратор V1 и domain-ошибку с машинно-читаемой причиной. Он
не импортирует Pydantic, API, SQLite, browser storage или infrastructure.

Предусмотрены два разных режима:

1. **Строгий V2.** Любое неизвестное поле, неверный тип или нарушенный инвариант
   отклоняет документ целиком. Частичное исправление нового документа запрещено,
   чтобы ошибки клиента не скрывались.
2. **Совместимый V1.** Корректный корень версии 1 переносится терпимо: известные
   валидные значения сохраняются, отсутствующие или неверные settings получают
   defaults, а отдельные повреждённые попытки отбрасываются. Повреждение одного
   элемента не уничтожает всю историю.

V1 распознаётся только при точном integer `version: 1`; `true`, `1.0`, строка
`"1"`, неизвестная версия и некорректный тип корня не считаются legacy-документом.
Миграция не изменяет переданный объект.

Правила миграции V1:

- отсутствующий `updatedAt` заменяется Unix epoch; невалидный — также epoch;
- отсутствующий или неверный `settings` заменяется defaults по отдельным полям;
- `lastVariant` сохраняется только как допустимая строка, иначе становится `null`;
- `fastMode` сохраняется только как boolean, иначе становится `false`;
- `runs` должен быть списком не более 200 элементов; больший список отклоняется
  как `history_too_large`, а неверный тип — как `invalid_document`;
- каждый run нормализуется независимо; непригодный элемент пропускается;
- дубликаты run ID удаляются, затем остаются первые 100 валидных попыток;
- невалидный `activeRun` становится `null`;
- неизвестные legacy-поля отбрасываются;
- результат всегда проходит строгую V2-валидацию до возврата.

Общие migration fixtures описывают вход, ожидаемый V2 или ожидаемую ошибку. Их
используют Python- и JavaScript-тесты, чтобы обе реализации не расходились.

## API, service и repository

### Transport schema

`src/trainer/api/schemas.py` получает отдельные вложенные модели
`ProgressV2`, `ProgressSettings`, `ActiveRun` и `CompletedRun`. Все V2-модели
запрещают extra fields и используют strict types. `ProgressRequest.progress`
различает точную версию 1 и строгую версию 2 без неявного числового coercion.

V1 остаётся только compatibility-входом в domain-мигратор; он не становится
вторым постоянным публичным контрактом. Ответы GET после внедрения всегда V2.

Нарушение строгой Pydantic-схемы нового V2 возвращает существующий стандартный
HTTP 422 с code `validation_failed`. Семантическая domain-ошибка входного legacy-
документа возвращает HTTP 400 `invalid_request`. Превышение legacy-предела 200
сохраняет понятное сообщение о слишком большой истории.

### ProgressService

- `get(user_id)` читает repository record и при отсутствии записи возвращает
  прежнее пустое состояние API;
- сохранённый V1 нормализуется в V2 в памяти и выдаётся клиенту без фоновой записи
  в БД;
- сохранённый валидный V2 проверяется и выдаётся в каноническом виде;
- `put(user_id, document)` принимает распознанный V1 или V2, приводит его к
  каноническому V2 и сохраняет только V2;
- server `updated_at` по-прежнему получается из injected clock и не смешивается
  с клиентским `progress.updatedAt`;
- сервис не объединяет документы: merge остаётся frontend-ответственностью.

Ленивая миграция GET намеренно не пишет в БД. Это делает чтение безопасным,
исключает неожиданные write-lock и позволяет откатить релиз. Следующий успешный
PUT закрепляет V2.

### Повреждённые сохранённые данные

Repository port получает нейтральную ошибку повреждённого документа.
SQLite-adapter переводит в неё ошибку JSON-декодирования или JSON-корень
неподдерживаемого типа. Service также считает несовместимым документ с неизвестной
версией или неустранимой domain-ошибкой.

GET в таком случае возвращает контролируемый HTTP 409 с code
`progress_data_incompatible` и пользовательским сообщением о несовместимом
формате сохранённого прогресса. Запись не перезаписывается и не сбрасывается.
Frontend сохраняет локальную копию и сообщает, что синхронизация временно не
выполнена. Ошибки соединения и прочие repository errors не маскируются этой
ошибкой.

SQLite хранит тот же JSON-документ и timestamp в существующей таблице
`user_progress`; Alembic-ревизия не требуется.

## Frontend и localStorage

Новые ключи:

- guest: `egeChineseProgressV2`;
- account: `egeChineseProgressV2:user:<id>`.

При загрузке область хранения определяется как сейчас. Алгоритм для каждой
guest/per-user области:

1. Прочитать и строго проверить V2-ключ.
2. Если V2-ключ отсутствует, прочитать соответствующий V1-ключ.
3. Нормализовать V1 в памяти теми же правилами, что domain.
4. Сначала успешно записать V2; только после этого удалить V1-ключ.
5. Если запись V2 завершилась ошибкой (например, quota/security), оставить V1 и
   продолжить с нормализованной in-memory копией.

Если V2-ключ существует, но повреждён, он не подменяется молча V1: frontend
использует безопасный default в памяти, сохраняет повреждённую строку и сообщает
об ошибке storage. Это предотвращает скрытую потерю данных. Новая запись может
заменить повреждённый V2 только после явного пользовательского действия,
изменившего прогресс.

`defaultProgress`, создание/завершение запуска и `mergeProgress` работают только
с V2. До merge локальный и серверный документы уже нормализованы. Merge сохраняет
текущую политику:

- объединить попытки по ID, отдавая при совпадении приоритет локальной копии;
- отсортировать их по времени завершения/старта от новых к старым и оставить не
  более 100;
- взять settings и activeRun из документа с более новым клиентским `updatedAt`;
- обновить итоговый `updatedAt` текущим временем после фактического изменения.

Переключение guest/account продолжает работать, но дополнительно мигрирует
соответствующие старые per-user ключи. Удаление старых ключей выполняется только
после подтверждённой записи V2.

## Совместимость и вне объёма

Сохраняются:

- HTTP-пути, авторизация и student-only доступ;
- envelope ответов и отдельный серверный `updatedAt`;
- frontend merge и debounce синхронизации;
- пользовательская история, active run и настройки;
- использование завершённого run как пока ещё свободного review snapshot;
- SQLite-таблица и опубликованные миграции.

Не входят в этап:

- strict schema поля `ReviewRequestCreate.run`;
- strict schema `MaterialRequest.content`;
- server-side merge, optimistic locking или разрешение конфликтов;
- изменение quick/fast mode;
- переезд истории в отдельные строки БД;
- удаление старых V1-ключей до успешной миграции;
- фоновая массовая миграция строк SQLite.

## Проверка

### Python

- domain unit: точный V2 round trip, strict types, extra fields, timestamp,
  границы и связи tasks, состояния active/completed run, лимиты и дедупликация;
- V1 migration unit по общим fixtures: defaults, сохранение корректных данных,
  отбрасывание отдельных плохих runs, corrupt activeRun, неизвестные поля,
  200/201 элементов и строгий тип версии;
- service unit: lazy GET migration без save, canonical PUT, clock, no mutation,
  отсутствие записи и mapping повреждённого repository document;
- SQLite integration: чтение V1, запись только V2, corrupt JSON, unknown version,
  Unicode, commit/rollback и изоляция пользователей;
- API integration: V1 PUT→V2 GET, strict V2 422, legacy semantic 400,
  сохранённый incompatible document 409, auth/role и round trip.

### JavaScript и browser

- JS unit использует общие fixtures и проверяет parity миграции;
- отдельные тесты проверяют strict V2 load, guest и per-user key migration,
  порядок write-before-delete, сохранение V1 при ошибке записи, merge/dedupe/limit
  и новые документы runner-а;
- Playwright заранее помещает реальную V1 guest-историю в `localStorage`, открывает
  приложение, проверяет видимую историю, появление V2, удаление V1 и продолжение
  тренировки без сброса;
- существующие сценарии синхронизации аккаунта и review request остаются зелёными.

### Обязательные команды

После реализации:

```bash
make check
make test-e2e
```

Документация архитектуры обновляется описанием V2 и lazy migration. Задача не
считается завершённой без свежего успешного вывода обеих команд и ревью diff.
