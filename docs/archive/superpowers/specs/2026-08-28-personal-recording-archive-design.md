# Личный аудиоархив и срок хранения записей

## Цель

Зарегистрированный ученик может прослушивать ответы из личного кабинета в
течение шести календарных месяцев после их создания. Гость тренируется без
серверного хранения аудио. По истечении срока доступ к записи закрывается и
файл удаляется из приватного storage с устойчивым повтором при временной
ошибке.

## Границы

- Сохраняются все завершённые аудиозаписи зарегистрированного ученика:
  отдельные ответы к заданию 1 и ответы к заданиям 2–3.
- Гостевые `Blob` и object URL существуют только в памяти браузерной вкладки.
  Клиент не вызывает archive API и не передаёт гостевое аудио на сервер.
- Отправка на разбор преподавателю остаётся добровольной. Она продолжает
  создавать отдельную приватную копию для очереди разбора; срок хранения
  этой копии также равен шести месяцам.
- В задачу не входят расшифровка, изменение правил оценивания, публичная
  выдача аудио или хранение файлов в `user_progress`.

## Пользовательский сценарий

1. В каталоге и на главном экране гость видит компактное сообщение:
   «После регистрации доступны остальные варианты и личный архив записей».
   Оно ведёт к существующему диалогу входа.
2. Во вкладке регистрации до кнопки создания аккаунта показано явное
   уведомление: «Ответы сохраняются в личном архиве на 6 месяцев, затем
   удаляются автоматически».
3. После завершения тренировки фронтенд загружает записи только при наличии
   авторизованного пользователя. Ошибка архива не отменяет результат
   тренировки и не блокирует скачивание текущих файлов; пользователю
   показывается понятный статус, что архив не синхронизирован.
4. В уже существующем окне «История» добавляется раздел «Мои записи».
   Каждая строка содержит вариант, номер задания/вопроса, `<audio controls>`
   и дату удаления. Отсутствие записей показывается отдельным пустым
   состоянием.
5. Ученику доступен только его архив. Преподаватель не получает к нему
   доступ; для разбора используются отдельные review-записи после явной
   отправки ученика.

## Данные и API

Новая таблица `personal_recordings` хранит только метаданные:

- `id`, `student_id`, `run_id`, `variant_id`, `task_number`,
  `question_number`, `label`;
- `storage_key`, `mime_type`, `size_bytes`, `duration_seconds`;
- `created_at`, `expires_at`.

Ограничение уникальности фиксирует одну позицию записи на `(student_id,
run_id, task_number, question_number)`. Ключи размещаются в приватном
`AUDIO_DIR` под отдельным префиксом `personal-recordings/`.

Добавляются защищённые authenticated endpoints:

- загрузка метаданных и тела одной записи текущего ученика;
- список неистёкших записей текущего ученика;
- потоковая выдача конкретной записи только её владельцу.

Контроллер проверяет MIME-тип, размер и позицию задания теми же правилами,
что review-загрузка. Файл сначала записывается в storage, затем метаданные
фиксируются транзакцией. При ошибке после записи ключ ставится в существующую
устойчивую очередь удаления.

`review_request_recordings` получает `expires_at`. Новые и существующие
review-записи получают срок, вычисленный от `created_at`, поэтому старые
файлы не становятся бессрочными.

## Срок и удаление

Срок равен шести календарным месяцам от `created_at` в UTC. Расчёт выполняет
прикладной код, а не конкретный диалект SQL, чтобы SQLite и PostgreSQL
получали одинаковое правило.

Операция истечения срока работает пакетами:

1. В одной транзакции выбирает истёкшие personal- и review-записи.
2. Удаляет их метаданные из БД, поэтому API сразу возвращает 404.
3. Добавляет их `storage_key` в `storage_cleanup_jobs` в той же транзакции.
4. После commit существующий processor удаляет файлы. Неудачная операция
   остаётся в очереди и повторяется без повторного открытия доступа.

`scripts.cleanup_storage` сначала выполняет эту операцию истечения, затем
обрабатывает очередь. Он безопасен для ежедневного запуска и дополнительно
вызывается best-effort при старте приложения. В runbook фиксируется ежедневный
cron/systemd timer с этой командой и проверка `pending=0`.

Удаление аккаунта также собирает ключи personal-архива вместе с review-файлами
и передаёт их в существующую очередь очистки.

## Изменения интерфейса

- В `material-list` и каталоге отображается гостевой callout. Для
  авторизованного пользователя он не рендерится.
- В форме регистрации уведомление видимо только в режиме `register`;
  переключение на вход скрывает его без изменения валидации формы.
- Модальное окно истории получает архивный список и статус синхронизации.
  Обновление стиля следует существующей бордово-золотой дизайн-системе.
- Локальная кнопка «Очистить историю» не удаляет серверный аудиоархив:
  она сохраняет прежнюю семантику очистки списка тренировок.

## Безопасность и ошибки

- Гостевой браузер не отправляет аудиофайлы на API.
- Все archive endpoints требуют аутентификации и фильтруют строки по
  `student_id`; угадывание ID возвращает 404.
- Аудио никогда не попадает в `public/`, URL выдаются только через
  авторизованный потоковый endpoint.
- Незавершённая/ошибочная загрузка очищается через очередь. Статус архива
  отображается без раскрытия ключей storage или внутренних ошибок.

## Проверка

- Domain/unit: календарный расчёт срока, выбор истёкших строк, постановка
  ключей в cleanup queue, повтор после сбоя storage.
- Migration/integration: чистая SQLite и обновление существующей SQLite/PG
  схемы; backfill `expires_at` для review-записей; account deletion включает
  personal archive.
- API/integration: гость получает 401 на archive endpoints, владелец видит и
  скачивает только свои записи, другой пользователь получает 404, истёкшая
  запись не читается до физического удаления.
- Browser: гость не выполняет archive upload; зарегистрированный ученик
  завершает задание, видит запись и дату удаления в истории; регистрация и
  каталог показывают требуемые уведомления.
- Полный прогон: `make check`, `make test-e2e`, а для изменённого storage —
  smoke из `DEVELOPMENT.md` при наличии соответствующей среды.
